# Dual-source transition: `btnyc.json` → `ssot/btnyc_source.json`

Rule: **R-SYSTEM-DUALSOURCE** ("Two Live Sources Are a Bounded Migration, Never a Steady State"). Opened by T175; **reconciled T176** against the Charter and the corrected Layer Map (`ssot/ENTITY_FIRST_DESIGN_NOTE.md` section 3.1 quotes the passages and classifies them). This is the transition ledger for it: the six fields the rule requires, the one fact a reader needs about which side is authoritative, and how an edit is made while both exist. The detector reads this file; the fields below are parsed, so keep their labels.

**What is being retired is a role, not a file name.** The Charter names `btnyc.json` as the derived runtime artifact ("`btnyc.json` is the derived runtime artifact the engine consumes; it carries a provenance reference to the source"). The retired thing is the hybrid `btnyc.json`: a file that is both hand-maintained authored knowledge and the runtime's input, with the compiler's generated keys mixed in. T175 wrote the completion as "`btnyc.json` is removed from the repository root"; that contradicted the Charter on the name and is replaced below.

## What is authoritative, and how an edit is made while both exist

- **The source (`ssot/btnyc_source.json`) is authoritative.** It holds everything `btnyc.json` authors, plus what `btnyc.json` could not say: entity ownership, `entity_scope`, uncertainty classes and weights, confidence gates and policies, retirement relations, recovery affordances, decompositions. `btnyc.json` is no longer where a decision is made.
- **No tool edits the source.** Until the CMS or a source-editing tool exists, the source is edited as JSON by hand and judged by the validator; this is the temporary direct-edit path that R-SYSTEM-CMS permits as a bounded dual-source transition. It is the only human edit path to the knowledge; the mirror is not a second one.
- **A change that `btnyc.json` can express** (an answer, a fee, a prompt, a branch, a picker tile, a tag) is made in the source first, then carried into the mirror `btnyc.json` by `test_harness/tools/ssot_patch.js … --write`, then `node test_harness/tools/entity_first/carry_charter.js --write` (the Charter overlay, below), then `python3 test_harness/tools/splice_compiled.py btnyc.json --write`, in the same commit. `node test_harness/tools/entity_first/project_legacy.js --check` and `verify_entity_first_migration.js` fail on a pair that disagrees. A change made only in `btnyc.json` fails the same check; a change made only in the source that `btnyc.json` can express fails it too.
- **S1 to S5 of `RESHAPE_SCOPE_S1_S6.md` are not applied as patches to the mirror.** Their data halves are realized in the source (ids on every option, one reference spelling, ids not labels, no compiler-owned keys). A patch that moves the mirror toward that shape makes it differ from the projection of the source, and `project_legacy.js --check` fails it by design. The legacy `ssot_patch.js` and `splice_compiled.py` stay intact for the legacy shape; they edit the mirror and never the new source. After completion they are retired with the mirror.
- **The Charter overlay in `btnyc.json` is generated, never edited (T181).** The Charter says what a record of the derived artifact carries; the authored source has all of it, and the live file now does too: `carry_charter.js --write` writes it onto the legacy records in place (a stable typed id on every entity, question, option, service, composition, tag, material, furniture item, formula, checkout state, category and group; `entity_scope` on each question; `affects` on each option; `depends_on` as `{question_id, option_id}` pairs; `uncertainty_profile`, `confidence_policy`, `confidence_gate` and `recovery_affordances` on each service and composition; `entity_id`, `action_id`, `modifier_ids` and the three-axis `complexity_profile`) and adds `$source` and the registries the ids point at (`entities` with their uncertainty classes and what retires them, `shared_uncertainty_classes`, `contexts`, `actions`, `modifiers`). It is additive on every record the page reads, with one exception: a module's `depends_on` changes spelling from `{module key: label}` to the pairs (6 modules; the two runtime readers, the compiler and three tests read both). A typed id lives in `id` where the legacy record had none and in `charter_id` where it already had a bare `id` the page reads (services, compositions, categories, groups). `carry_charter.js strip` is the exact inverse, and `lib.authoredLegacy` applies it, so every parity tool still compares the pre-carry shape. `carry_charter.js --check` fails on a hand edit, a stale value, a missing member or a member the source no longer produces; `verify_charter_carry.js` holds the file to the seven obligations and to the schema, with counterfactuals.
- **A change `btnyc.json` cannot express** (a scope on a shared question, a decomposition, a recovery question not yet carried) is made in the source only. It is checked by the validator (`validate_source.js`) and re-derived (`derive_graph.js`); the parity check does not see it, by design. Anything the Charter requires on a record is carried by the overlay, so the source is the only place it is edited.
- **A new id is registered, a removed or renamed id is retired.** `node test_harness/tools/entity_first/id_register.js --write` appends new ids; removing or renaming one needs a written retirement in `ssot/migration/id_register.json` (reason, replacement, ledger ticket), or `verify_entity_first_id_freeze.js` fails.
- **After a derived artifact changes**, regenerate it: `node test_harness/tools/entity_first/publish.js` (not `derive_graph.js` directly: the publisher is the one writer and refuses an invalid source) and `node test_harness/tools/entity_first/report.js --write`. `publish.js --check` and `report.js --check` are in the suite, so a stale or hand-edited graph or report cannot land.
- **`migrate_legacy.js --write` does not overwrite an edited source.** It replaces the source only if the source is exactly what the last migration wrote (`ssot/migration/last_migration.json`), and refuses otherwise (exit 3) unless `--overwrite-authored` is passed. The migration is the one-time carry of `btnyc.json`; it is not a way to edit the source.

## What is duplicated, and what is not

| Fact | In `btnyc.json` | In the source | Drift detected by |
|---|---|---|---|
| Answers, prompts, fees, branches, pricing, tags, picker content, vocabulary, policy | yes (labels as keys, `then` maps) | yes (ids, `{question_id, option_id}` terms) | `project_legacy.js --check`: the projection of the source equals every authored section of `btnyc.json`, except the pinned normalizations |
| The eight compiler-owned keys (`compiled`, `routing_archetypes`, …) | yes (derived) | **no** (not authored) | `compiler_roundtrip.js`: the unchanged compiler, run on the source alone, reproduces all eight |
| Entity ownership, scope, uncertainty, confidence, retirement, recovery, decompositions | **yes since T181, as a generated overlay** (not an authority) | yes (authoritative) | `carry_charter.js --check` (the overlay is exactly what the source says; a hand edit or a stale value fails), `verify_charter_carry.js` (the seven obligations, measured on the file), `validate_source.js` (the source itself) |
| The three axes every service declares (T180, `R-COMPLEX-AXES`): `complexity_profile` on each service and the vocabulary `policy.complexity_axes`. The skill tier is the one `btnyc.json` already declares (`operational_metrics.complexity_tier`); the risk tier, the batch-risk flag and the grounds of each are authored in `ssot/migration/complexity_axes.json` and copied by the migration | **`complexity_profile` yes since T181 (overlay)**; the skill tier is also its own legacy field | yes (authoritative) | `validate_source.js` V-COMPLEX-* (the profile's tier must equal `operational_metrics.complexity_tier`; the risk tier is the highest hazard named; the flag is true exactly when a ground is named, and a signal in the service's own record must be named) and `verify_complexity_axes.js` |
| The derived graph | no | derived from the source | `derive_graph.js --check`: the committed graph is what the source derives |

The differences the parity check tolerates are pinned, in both directions, in `test_harness/tools/entity_first/declared_normalizations.js`. A difference that is not pinned fails; a pinned one that no longer occurs fails.
