## 3. Architecture, as it is today (not as the target)

- **The page.** `qr.html` is one file. Five modules are inline blocks (`pricing_engine`, `orchestrator_engine`, `UIRenderer`, `cart_logic`, `AppController`); four are files in `modules/` loaded by `<script src>` (`trace`, `nlp_engine`, `appReducer`, `store`). For an inline module the block in `qr.html` is the source. The `*.js` files of the same names at the repository root are **generated, git-ignored reference copies** (`node test_harness/extract_modules.js`; rerun after any `qr.html` edit). `purity_audit.json` is a derived but tracked output.
- **Two catalogs while the dual-source transition is open (T175).** `ssot/btnyc_source.json` is the **entity-first authored source** and is authoritative (entities own their questions, uncertainty classes and services; services are entity + action + modifiers; ids everywhere; confidence, retirement and recovery are authored); `btnyc.json` is what the runtime and the compiler still read and is kept in parity with it (`node test_harness/tools/entity_first/project_legacy.js --check`). A change `btnyc.json` can express is made in both in one commit; a change it cannot express (a weight, a scope, a retirement, a decomposition) is made in the source only. After a source change run `derive_graph.js` and `report.js --write` (their `--check` modes are in the suite). The rules are in `ssot/TRANSITION_DUALSOURCE.md`. `migrate_legacy.js --write` refuses to overwrite an edited source. The next bullet describes `btnyc.json`, not the source.
- **The catalog (`btnyc.json`).** `btnyc.json` (about 45,000 lines) is **service-first, not entity-first**: 76 `services`, 82 `dynamic_services`, 135 `intake_modules`, 59 `smart_tags`, 39 groups with `routing_archetypes`, plus `checkout_states`, `pricing_archetypes`, `global_rules` and compiler-owned `compiled`. There is no `entities` key in it; the entity-first shape the Playbook describes exists in `ssot/btnyc_source.json`, not in this file.
- **The compiler.** `test_harness/btnyc_v10_compiler.py` validates and derives; `test_harness/tools/splice_compiled.py btnyc.json [--write]` regenerates the compiler-owned keys (must report "0 of 8 differ" when idempotent; it does today). Edit the catalog with `node test_harness/tools/ssot_patch.js <patch.json> btnyc.json --write` (ops set/add/rename/append/delete/expect), then splice.
- **One gateway.** `executeWorkflow` (orchestrator) is where every entry path resolves: catalog tap, free text, the Other tile, an answered chip. It runs `orch_run_workflow`, then follows any `route_to` on an answered option (bounded by `ROUTE_TO_MAX_HOPS = 3`, never re-entering a visited service). `orch_route_still_possible` / `route.triagePending` hold the Fork until a question that could name the part has been asked. Pricing is `computeUnifiedQuote` (state path) and `orch_compute_quote` (orchestrator path), both reading `resolveChargeableAnswers`.
- **The Fork in the Road.** A quote whose checkout state is `diagnostic`, on an entity with `remote_deep_dive_modules`, offers Path A (more questions, hourly estimate) or Path B (on-site diagnostic, $85 flat, credited toward the repair via `global_rules.divergence_resolution`).
- **Tests.** `test_harness/` held 253 files at the T174 closeout (T175 added the four tests above and `tools/entity_first/`); `MASTER_TEST_SUITE.json` lists 215 tests on `ssot-entity-first` (211 on `t174-landing`; T175 added `verify_entity_first_validator.js`, `_migration.js`, `_references.js` and `_transition.js`); `test_harness/run_all.sh` and `node test_harness/tools/suite_snapshot.js --out X.tsv [--compare baseline.tsv] --jobs N` run them. The comparison gate fails on pass→fail, and on a red test reporting more failing assertions or losing its count.
- **Where the rules are.** `PROJECT_CHARTER.html` (rule codes such as `R-CLIENT-CONVERGE`, `R-SYSTEM-NODATA`, `P-INTAKE-INFER`); `COMPONENT_LAYER_MAP.md` (module/layer table, the `BookingContext` contract; its line numbers drift and must be re-verified).
